# Enough Desktop Agent

Phase 11 source for the Windows, macOS, and Linux desktop agent. The app uses an Electron system tray, shared Enough classification and policy code, local app and idle monitoring, a grace-period focus reminder, and the existing auth, rules, overrides, and activity APIs.

## Start locally

From the monorepo root:

```sh
pnpm install
pnpm desktop:start
```

Sign in with a verified email and password, or paste a desktop access token created in Enough account settings. Choose a product, then start Build or the 60-minute Growth session. The tray menu has the same session, pause, sync, and quit controls.

## Native browser bridge

Build the app sources, then register the native messaging host for the browser extension:

```sh
pnpm --filter @enough/desktop native-host:install -- --browser=chrome --chrome-origin=chrome-extension://abcdefghijklmnopabcdefghijklmnop/
```

Replace the example with the exact origin shown for the installed extension. Use `edge`, `brave`, `firefox`, or `all` for `--browser`. For `all`, pass the exact Chromium origin(s); Firefox uses the add-on ID `enough@example.com` by default. On Windows, the command registers the host in the current user's browser registry keys. Restart the browser and keep the Enough tray agent running. The native host reports agent health only; it does not forward app names or window details to the extension.

This source setup uses the Node executable that runs the installer. A production installer still needs to ship a standalone native host executable for each platform and register that executable. The source native host can be launched with Node on a development machine.

## Local behavior and privacy

- Active-window detection reads the owning app identifier and display name. The agent does not read or store window titles, browser tab URLs, source code, or window contents.
- Idle time and system lock signals pause app timing and focus enforcement. On Linux, active-window monitoring requires X11; Wayland does not expose the foreground app through the current detector. Linux lock-state reporting also depends on the desktop environment.
- Local session state, cached policy, app-time totals, and pending events are encrypted through Electron `safeStorage`. Sign-in is disabled when an OS keychain or keyring cannot encrypt the cache. Keep the account session revoked if the device is lost.
- App-usage sync is off by default. When enabled, events contain the app identifier, classification, policy action, mode, and active seconds. Window titles and browser URLs are never uploaded.
- The encrypted cached policy is used offline for up to 24 hours. The agent detects a material wall-clock jump while it is running and a backward change compared with its last stored clock observation; either condition pauses enforcement until a successful policy sync. Forward clock changes while the app is stopped cannot always be distinguished from real offline time, though large jumps expire the cache. The app shows a warning and does not claim that the cached policy is tamper-evident: the API does not yet sign policy snapshots.
- App-time totals and restricted-app grace periods use monotonic elapsed time so wall-clock changes do not inflate usage or unexpectedly extend/shorten the reminder grace period. Offline activity is bounded to 1,000 queued events and seven days; discarded events are counted and shown in the app.
- A restricted foreground app first triggers a native notification. After the selected 30-second to 5-minute grace period, a full-screen reminder appears. The agent does not terminate apps or discard work. Switching to an allowed app closes the reminder. A reasoned 5-to-60-minute emergency override is cached locally and queued for API sync if offline.
- Build and Growth sessions, app monitoring, and policy evaluation use the existing server rule definitions and shared TypeScript evaluator. Packaged builds read the update provider generated by electron-builder: GitHub Releases when `GITHUB_REPOSITORY` is set, or a public HTTPS generic feed when `ENOUGH_UPDATE_URL` is set at build time. Production installers require platform signing and macOS notarization; see `RELEASES.md` for the tagged release workflow and required secrets. Installer delivery, signatures, update installation, and native-host installation still need platform acceptance.

## Acceptance status

The source is present; desktop builds, installer signing, keychain behavior, native host installation, Linux desktop variants, app-policy enforcement, offline reconciliation, and update delivery have not been built or accepted yet. Application identity uses bundle ID, executable basename, and display name rather than verifying a code signature, so a renamed process may resolve as a new app. Linux Wayland active-app enforcement is unsupported by the chosen foreground-window API.
