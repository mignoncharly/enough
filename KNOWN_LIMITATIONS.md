# Known Limitations

Last updated: 2026-10-13

- Phases 1–10 have accepted implementation and runtime evidence recorded in their phase acceptance files. Later-phase acceptance remains separate and incomplete where noted below. Phase 23 has 65 passing unit/property/contract tests and successful desktop/extension source builds; later live database, runtime, and full critical-path coverage remains incomplete. Phase 24 has configured installer targets, auto-update feeds, a release workflow, and generated extension store ZIPs, but signed installers, store publication, and install/update acceptance remain incomplete. The local desktop packaging attempt is blocked by `EPERM` reading electron-builder's linked `dotenv` dependency.
- Phase 25 adds Ubuntu, Nginx/TLS, systemd, deploy/rollback, encrypted PostgreSQL backup, isolated restore-test, journald, and readiness-monitor templates. No production host has been configured or deployed; TLS, reboot recovery, remote backup, and restore acceptance remain pending. The readiness timer records failures in journald but has no external alert integration. Code rollback does not reverse database migrations.
- Phase 26 production verification is pending: no application or infrastructure service is listening locally, no production host/credentials are configured, and no end-to-end integration scenarios have run. Gmail, Outlook, calendar, Stripe revenue, and analytics adapters are implemented in source but still require provider acceptance; signed desktop/store releases also remain prerequisites for their checks.
- Phase 27 launch gate is NO-GO. Required capabilities are source-only or unverified, Phase 14's six external real-provider gates remain open, signed installer/store and auto-update acceptance are incomplete, and there is no production deployment. All 18 dependency-security findings remain open. See `LAUNCH_READINESS.md` for the full matrix.
- Stage-specific priorities, tasks, and build to market ratios are deterministic advisory guidance; they do not enforce policies.
- Local email links require `AUTH_DEV_SHOW_EMAIL_LINKS=true` or configured Resend credentials. OAuth buttons are available only when provider credentials are configured.
- Phase 11 remains ACTIVE: Windows P11-1, P11-2, and P11-3 passed consolidated manual acceptance. P11-4 is BLOCKED by the restriction against modifying browser profiles/protected configuration; P11-5 is BLOCKED because signed updater/package credentials and required macOS/Linux runtime environments are unavailable. Desktop policy uses Ed25519-signed, account/device-bound snapshots with a 24-hour maximum validity. Production signing-key/release configuration, signed packaged updater/install acceptance, and platform runtime acceptance remain outstanding. A forward clock change while the client is stopped cannot always be distinguished from actual offline time. Linux Wayland active-app detection is unsupported, and Linux lock-state reporting varies by desktop environment.
- Passkeys are deferred; the provider capability endpoint reports them as unavailable.
- Historical Phase 1 migration-runner failures below refer to earlier environments and do not supersede accepted Phase 1–10 evidence; the isolated current fixture applied and prechecked migrations through `0017` for Phase 10.
- Phase 4 adds products, stage history, goals, and metric observations. Phase 5 adds per-device ordered activity events and hourly aggregates. Clients must not send personal or secret values in event attributes.
- Phase 6 adds a seeded catalog and deterministic account/product/context mappings for applications and domains. `BLOCKED` and `ALLOWED` describe a classification; the rule engine can use them as policy conditions.
- Phase 7 adds policy decision evaluation and temporary overrides, now consumed by the Phase 10 extension and Phase 11 desktop agent. Scheduled decisions depend on the server-supplied evaluation instant and time-zone database; deterministic evaluator tests and runtime acceptance passed and are recorded in `PHASE_7_ACCEPTANCE.md`.
- Phase 8 adds wallet-scoped idempotency, account-row locking, grant expiry, reservation management, and refund tracking. Multi-device concurrency remains unverified. Manual earn and adjustment routes remain owner-authenticated controls; they are prototype controls, not billing or proof of completed work.
- Phase 9 adds shared navigation, theme preference, activity history, device/session management, and summary pages. Its consolidated browser acceptance passed (P9-1–P9-5; see `PHASE_9_ACCEPTANCE.md`), including responsive layouts, accessibility, and error/empty/permission states. `/products` currently routes to product controls on `/dashboard`; Activity and Reports show submitted event data (Reports cap at 100 returned events). Evidence, signed inbound Integrations, and Billing include future-state empty behavior in the Phase 9 surface; their later phase workflows retain separate acceptance requirements.
- Phase 10 Chromium/Firefox builds, focused client tests, workspace typecheck, isolated full-stack readiness smoke, and consolidated browser acceptance P10-1–P10-5 passed (`PHASE_10_ACCEPTANCE.md`). It enforces top-level navigation only, evaluates at most 900 candidate domains per sync, and pauses local enforcement when cached policy is over 24 hours old or a material clock change is detected. Forward clock changes while the browser is stopped cannot always be distinguished from real offline time. A disabled extension cannot enforce policy; on restart, stale Enough-owned dynamic rules are cleared. Domain tracking is off by default; when enabled it records hostnames only. The bearer token is stored in extension local storage, not encrypted. The Phase 11 native host is not installed; the extension reports that health state as unavailable.
- Phase 12 adds stage templates, custom tasks, recurring occurrences, signal strength, priority, time estimates, due dates, and task rewards. Recurring tasks create the next occurrence after completion. New task rewards now wait for Phase 13 evidence verification; previously issued Phase 12 rewards remain marked `SELF_REPORTED` and are not duplicated. Migration and runtime acceptance remain pending.
- Phase 13 stores self-reports, notes, HTTP(S) URLs, uploads, screenshots, and user-submitted integration references. Manual review uses the product owner's account, so it is auditable but not independent verification. Files are private PostgreSQL BYTEA records, limited to 2 MiB each, 20 MiB per account, and 200 evidence items per account; only PNG, JPEG, WebP, and PDF are accepted, and screenshots must be images. Uploads are signature-checked but not malware-scanned. File privacy, quota enforcement, review idempotency, reward issuance, account export, and deletion still need runtime acceptance.
- Phase 14 migration `0020`, deterministic provider/API suites, and local browser acceptance passed. Generic webhook and Public Event API signatures still authenticate only the workspace owner's configured source. Provider-linked task evidence stays pending for owner review except for the narrow Stripe-confirmed payment path. Phase 14 remains ACTIVE pending real Google/Microsoft OAuth, dedicated PostHog/Plausible/GA4 test properties, and Stripe end-to-end customer-revenue webhook delivery. Production remains NO-GO with all 18 dependency-security findings open.
- Phase 21 queues offline client events for at most seven days and 1,000 entries; overflow and expiry counts are visible in the client. Activity event IDs are idempotent, and client sequence uniqueness is scoped to a device/product. Concurrent wallet and task-completion changes use database row locks in source, but migration and concurrency acceptance are pending. Revoked integration accounts are locked during event ingestion and revocation; race behavior remains unverified at runtime.
- Desktop application identity uses bundle ID, executable basename, or display name; it does not verify a code-signing identity. Renaming a process can therefore produce a new application key and fall back to the default policy. The desktop grace timer and app-time accumulator use monotonic time; signed snapshot expiry is checked against the system clock, which is not a trusted source across restarts.
- A task completion claim alone stays in `AWAITING_EVIDENCE` and does not grant credits. Evidence can be reviewed by the product owner, including the person who submitted it, so manual verification is auditable but not independent. Previously issued Phase 12 self-reported rewards remain historical records.
- The worker currently accepts only its `healthcheck` job type; business jobs are added with their owning phases.
- Readiness verifies PostgreSQL and Redis connectivity, not downstream application behavior.
- Phase 22 Admin Console access requires a verified account email listed in `ADMIN_EMAILS` for bootstrap, or a database-backed ADMIN/SUPPORT role granted by an administrator. Admin operations, migration 0015, failed-job retry, and live health reporting have not been exercised. Feature flags affect runtime behavior only where application code reads a flag; rule templates remain an admin catalog and are not yet offered in the user rule editor. AI usage records are written only for OpenAI requests and contain request metadata and token counts, not prompt or response text.
- The Nginx template has TLS and split app/API routing, but uses example hostnames and depends on a certificate that has not been issued. It is not ready for public deployment until configured and validated on the production host.
- Direct Vitest execution previously passed the current suite. Typecheck remains blocked because the sandbox denies reads from the pnpm-linked TypeScript package. The earlier `pnpm test` attempt stopped at pnpm's ignored-build-script guard; `electron-winstaller` is now allowlisted and `pnpm install --frozen-lockfile` succeeds, but `pnpm test` has not been rerun.
