# Known Limitations

Last updated: 2026-10-07

- Phase 2 through Phase 22 source is present, but migrations `0002` through `0015` and runtime acceptance have not been completed. Phase 23 has 65 passing unit/property/contract tests and successful desktop/extension source builds; live database, runtime, and full critical-path coverage remain incomplete. Phase 24 has configured installer targets, auto-update feeds, a release workflow, and generated extension store ZIPs, but signed installers, store publication, and install/update acceptance remain incomplete. The local desktop packaging attempt is blocked by `EPERM` reading electron-builder's linked `dotenv` dependency.
- Phase 25 adds Ubuntu, Nginx/TLS, systemd, deploy/rollback, encrypted PostgreSQL backup, isolated restore-test, journald, and readiness-monitor templates. No production host has been configured or deployed; TLS, reboot recovery, remote backup, and restore acceptance remain pending. The readiness timer records failures in journald but has no external alert integration. Code rollback does not reverse database migrations.
- Phase 26 production verification is pending: no application or infrastructure service is listening locally, no production host/credentials are configured, and no end-to-end integration scenarios have run. Gmail, Outlook, and calendar vendor sync adapters and signed desktop/store releases remain product prerequisites for their checks.
- Phase 27 launch gate is NO-GO. Required capabilities are source-only or unverified, Gmail/Outlook/calendar provider adapters are missing, signed installer/store and auto-update acceptance are incomplete, and there is no production deployment. See `LAUNCH_READINESS.md` for the full matrix.
- Stage-specific priorities, tasks, and build to market ratios are deterministic advisory guidance; they do not enforce policies.
- Local email links require `AUTH_DEV_SHOW_EMAIL_LINKS=true` or configured Resend credentials. OAuth buttons are available only when provider credentials are configured.
- The Phase 11 desktop app and native messaging host source now exist, but builds, native-host registration, and end-to-end acceptance remain pending. Desktop offline policies are encrypted locally but not signature-verified. Expired or detected clock-inconsistent policy pauses local enforcement; a forward clock change while the client is stopped cannot always be distinguished from actual offline time. Linux Wayland active-app detection is unsupported, and Linux lock-state reporting varies by desktop environment.
- Passkeys are deferred; the provider capability endpoint reports them as unavailable.
- Phase 1 runtime acceptance remains pending. An earlier `pnpm db:migrate` attempt hit pnpm's no-TTY module-removal guard; `pnpm install --frozen-lockfile` now succeeds, but the migration runner still encounters denied reads from the linked package store. Migrations `0002` through `0015` have not been applied.
- Phase 4 adds products, stage history, goals, and metric observations. Phase 5 adds per-device ordered activity events and hourly aggregates. Clients must not send personal or secret values in event attributes.
- Phase 6 adds a seeded catalog and deterministic account/product/context mappings for applications and domains. `BLOCKED` and `ALLOWED` describe a classification; the rule engine can use them as policy conditions.
- Phase 7 adds policy decision evaluation and temporary overrides, now consumed by the Phase 10 extension and Phase 11 desktop agent. Scheduled decisions depend on the server-supplied evaluation instant and time-zone database; deterministic evaluator tests and runtime acceptance remain pending.
- Phase 8 adds wallet-scoped idempotency, account-row locking, grant expiry, reservation management, and refund tracking. Multi-device concurrency remains unverified. Manual earn and adjustment routes remain owner-authenticated controls; they are prototype controls, not billing or proof of completed work.
- Phase 9 adds shared navigation, theme preference, activity history, device/session management, and summary pages. `/products` currently routes to product controls on `/dashboard`; Activity and Reports show submitted event data (Reports cap at 100 returned events). Evidence, signed inbound Integrations, and Billing now have source implementations. Browser rendering, accessibility, responsive layouts, and error/empty/permission states have not been runtime-verified.
- Phase 10 adds the Chromium/Firefox MV3 extension source. Chromium/Firefox builds and store ZIP generation pass; browser installation, domain-rule parity, schedule and override boundaries, offline sync, and session rotation have not been verified. It enforces top-level navigation only, evaluates at most 900 candidate domains per sync, and pauses local enforcement when cached policy is over 24 hours old or a material clock change is detected. Forward clock changes while the browser is stopped cannot always be distinguished from real offline time. A disabled extension cannot enforce policy; on restart, stale Enough-owned dynamic rules are cleared. Domain tracking is off by default; when enabled it records hostnames only. The bearer token is stored in extension local storage, not encrypted. Phase 11 native-host source polls a heartbeat every five seconds and reports the desktop agent as degraded after 20 seconds without a fresh heartbeat; installation remains unverified.
- Phase 12 adds stage templates, custom tasks, recurring occurrences, signal strength, priority, time estimates, due dates, and task rewards. Recurring tasks create the next occurrence after completion. New task rewards now wait for Phase 13 evidence verification; previously issued Phase 12 rewards remain marked `SELF_REPORTED` and are not duplicated. Migration and runtime acceptance remain pending.
- Phase 13 stores self-reports, notes, HTTP(S) URLs, uploads, screenshots, and user-submitted integration references. Manual review uses the product owner's account, so it is auditable but not independent verification. Files are private PostgreSQL BYTEA records, limited to 2 MiB each, 20 MiB per account, and 200 evidence items per account; only PNG, JPEG, WebP, and PDF are accepted, and screenshots must be images. Uploads are signature-checked but not malware-scanned. File privacy, quota enforcement, review idempotency, reward issuance, account export, and deletion still need runtime acceptance.
- Phase 14 adds signed Generic webhook and Public Event API sources, normalized event storage, hashed external user references, idempotency, timestamp replay limits, API-key/IP rate limits, revocation, and credential-safe account export. The owner controls the signing source: a valid HMAC proves control of that source, not that a named vendor produced the claim. Linked task evidence stays pending for owner review and cannot directly grant credits. Gmail, Google/Microsoft calendars and mail, Stripe, PostHog, Plausible, and GA4 provider-specific OAuth, sync, and signature adapters are planned. Migration and runtime acceptance remain pending.
- Phase 21 queues offline client events for at most seven days and 1,000 entries; overflow and expiry counts are visible in the client. Activity event IDs are idempotent, and client sequence uniqueness is scoped to a device/product. Concurrent wallet and task-completion changes use database row locks in source, but migration and concurrency acceptance are pending. Revoked integration accounts are locked during event ingestion and revocation; race behavior remains unverified at runtime.
- Desktop application identity uses bundle ID, executable basename, or display name; it does not verify a code-signing identity. Renaming a process can therefore produce a new application key and fall back to the default policy. The desktop grace timer and app-time accumulator use monotonic time, but cached policy remains unsigned and the system clock is not a trusted source across restarts.
- A task completion claim alone stays in `AWAITING_EVIDENCE` and does not grant credits. Evidence can be reviewed by the product owner, including the person who submitted it, so manual verification is auditable but not independent. Previously issued Phase 12 self-reported rewards remain historical records.
- The worker currently accepts only its `healthcheck` job type; business jobs are added with their owning phases.
- Readiness verifies PostgreSQL and Redis connectivity, not downstream application behavior.
- Phase 22 Admin Console access requires a verified account email listed in `ADMIN_EMAILS` for bootstrap, or a database-backed ADMIN/SUPPORT role granted by an administrator. Admin operations, migration 0015, failed-job retry, and live health reporting have not been exercised. Feature flags affect runtime behavior only where application code reads a flag; rule templates remain an admin catalog and are not yet offered in the user rule editor. AI usage records are written only for OpenAI requests and contain request metadata and token counts, not prompt or response text.
- The Nginx template has TLS and split app/API routing, but uses example hostnames and depends on a certificate that has not been issued. It is not ready for public deployment until configured and validated on the production host.
- Direct Vitest execution previously passed the current suite. Typecheck remains blocked because the sandbox denies reads from the pnpm-linked TypeScript package. The earlier `pnpm test` attempt stopped at pnpm's ignored-build-script guard; `electron-winstaller` is now allowlisted and `pnpm install --frozen-lockfile` succeeds, but `pnpm test` has not been rerun.
